Overview

Classroom Token Hub (CTH) is a teacher-developed classroom management application with a simulated economy. Teachers configure classroom activities, attendance, payroll, checking and savings, rent, insurance, and store purchases.

This page explains account setup, classroom access, and data handling for schools and districts. See the Privacy & Data Handling policy for more details.

1. Data Collection, Processing, and Storage

Teacher setup

  • A username and authenticator setup; optional registered passkeys.
  • A two-part teacher display name, class name, optional section label, and class time zone.
  • Class settings, classroom content, and any submitted support reports.

Student setup

  • The teacher supplies first and last name fields as they should be entered during claiming. These may be full or partial names; the last field is not restricted to one initial.

    • privacy_tipUse non-identifying names for greater privacy

    While these fields are labeled as first name and last name, teachers can choose to use any identifier, such as nicknames, to further preserve student privacy.
  • The roster supports optional encrypted teacher notes. Keep unnecessary personal or sensitive information out of notes and other free-text fields.
  • The student enters the class join code, matching name fields, and a teacher-provided distinguishing code if duplicate roster names require one, then creates a username, PIN, and passphrase.

Stored records

Display names and roster notes use application-level Fernet encryption. Username and roster-name matching use keyed HMAC-SHA256 digests. PINs and passphrases use salted scrypt hashes. These protections apply to specific fields; they do not mean every database field is encrypted.

The application also stores classroom activity, support content, and technical diagnostic records. Names directly identify people. Activity stored under an opaque student reference is pseudonymous: the application can link it to a student, but an amount or timestamp is not itself a name. These linked records are not anonymous.

2. Class Boundaries and Shared Accounts

Classroom economy records belong to a particular class and student participation record. Teachers work in the selected class they own, and students access the classes they have joined.

A single sign-in account can participate in multiple classes. A signed-in student can add another class after matching that class’s roster. This shares account credentials across those memberships; it does not combine their balances, attendance, purchases, or classroom economy history. Matching names alone do not merge accounts.

System administrators handle support reports and operational information. Teachers can also share a hall-pass verification link with school staff, as described below.

3. Student Account Claiming

  1. The teacher provisions a roster entry and shares the class join code.
  2. The student enters the join code and first and last name fields matching that entry.
  3. If several entries match, the student enters the distinguishing code supplied by the teacher.
  4. The student creates a username, a 4–6 digit PIN, and a passphrase to finish setup.

4. Information Not Required for Accounts

Teacher and student account forms do not require email addresses, phone numbers, home addresses, dates of birth, parent contact details, government identifiers, or district student ID numbers. CTH does not provide an academic gradebook or connect to a district student information system.

This does not mean the application cannot contain sensitive information. Attendance, hall-pass destinations, classroom bonuses and fines, insurance claims, roster notes, and support explanations can describe student activity. Free-text fields are not a suitable place for medical details, disciplinary case records, contact information, or other unnecessary personal data.

If someone emails support, their email provider and the support mailbox necessarily process the message and sender address; email is separate from account registration.

5. Data Lifecycle and Deletion

Teachers have controls to remove students from a class, delete a class, and delete their teacher account. These invoke hard-deletion workflows, rather than an archive or restore feature. Removing one class membership does not remove a student’s memberships in other classes.

Teachers should delete classes when they are no longer needed. Teacher-downloaded exports are school-controlled copies outside application deletion; deleting a class does not delete those files. Contact support with retention or deletion questions.

6. Authentication and Security Controls

  • Teachers: username plus a time-based one-time password (TOTP) from an authenticator, or an enrolled passkey. The application does not use teacher email/password login.
  • Students: username and passphrase for sign-in. The PIN is used for attendance, transfers between checking and savings, and hall passes. Purchases, rent, insurance payments and cancellation, and other entitlement use require the passphrase.
  • Stored credentials: PINs and passphrases use salted scrypt hashes. Authenticator secrets are encrypted. Passkey registration stores a public key and credential metadata.
  • Recovery: a teacher can issue a student an eight-character code that expires after ten minutes. The recovery form asks for that code, then directs the student to create new credentials. Teacher recovery requires confirmation from one selected student in every class belonging to that teacher’s account, within a five-day window. See the account recovery details.
  • Sessions: signed, HTTP-only, SameSite=Lax cookies; the Secure flag is enabled in production configuration. Student sessions have a ten-minute limit from login; teacher sessions expire after ten minutes of inactivity.
  • Request protection: the application includes CSRF protection and rate limits. Selected forms use Cloudflare Turnstile when configured.

7. Application Access and Support Review

Teachers can see classroom rosters and activity, manage student participation, and download class roster or student exports. Students see their own display name and classroom information made available to them.

A system administration console exists. It presents operational logs, monitoring, teacher reports, and escalated student issues. Support review can include explanations, diagnostic notes, and snapshots of related classroom activity. Participant identity fields use opaque references, and a class label is shared with the console only when the teacher enables that option. Free-text submissions can still disclose what the author types.

Shared hall-pass verification

A person with a teacher’s verification link can select one of that teacher’s classes and submit a student’s first and last name. A matching result can display the student’s name, class, destination, pass status, and departure or return details for the current day. The page does not require a teacher or student login. Share the link only with intended school staff.

8. Hosting, Service Providers, and Encryption Limits

The application needs access to its encryption key to display protected fields. A person or process with both the database and that key can decrypt those fields. Field encryption does not make data inaccessible to every infrastructure administrator.

The public site is published through GitHub Pages and loads fonts from Google Fonts and styling from jsDelivr. The application integrates Cloudflare Turnstile when configured and supports operational monitoring. These services receive technical request information; Turnstile verification can include the visitor’s IP address.

See technical data and service providers for information about these requests. Contact support with questions about hosting and data handling.

9. Single Sign-On and Integration

The current application does not implement district SSO through SAML or OpenID Connect, district roster synchronization, or external student-ID matching. Registered passkeys are an application sign-in method; they are not district SSO.

The source repository (opens in a new tab) is available under the PolyForm Noncommercial 1.0.0 license. Review its conditions before self-hosting or modifying the application. A modified deployment needs its own review and privacy disclosures.

10. School Adoption and Accessibility

Schools and districts should review the intended educational use, authority to provide student information, required notices or consent, access, retention, and service providers before adoption.

Review the U.S. Department of Education’s FERPA guidance for service providers and the FTC’s COPPA guidance. The FTC limits school-authorized consent to the educational context; it does not remove the operator’s applicable obligations.

For help with keyboard navigation, screen readers, contrast, or another access need, contact support@classroomtokenhub.com.

11. Simulated Financial and Activity Records

CTH currency has no real monetary value. The application does not connect to banks or real payment processing.

It records classroom payroll, bonuses and fines, transfers, rent and other obligations, insurance, store purchases, and entitlement use. Balances are derived from ledger records; pending transactions can affect the amount available to spend. Corrections use recorded reversal or void workflows.

These records use class and student participation identifiers and can be linked back to a student by authorized application views. Amounts, timestamps, and ordinary activity fields are not all encrypted with the display-name encryption facility. Class-level economic summaries are available to teachers.

12. Use of Information

  • CTH does not display advertisements or sell user data.
  • Public pages request fonts and styling from the providers listed above.
  • Classroom summaries, operational monitoring, and support diagnostics are part of the application.
  • The application does not provide district SSO, a gradebook, or real banking services.

Contact Information

For district review, agreements, data access, correction, or deletion questions, contact support@classroomtokenhub.com. For security questions, contact security@classroomtokenhub.com.

Students and families should begin with the classroom teacher or school. Do not include passwords, PINs, recovery codes, or unnecessary student information in an email.
