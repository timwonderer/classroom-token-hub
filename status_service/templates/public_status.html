Request evidence
{{ icon('chevron_right', 'sm', 'chev') }}What the numbers mean

We check the app and its database every minute. A check expires after five minutes if polling stops, and it doesn't test every classroom action.

The areas above describe the requests we saw in the last five minutes. A quiet area shows when it was last seen, kept for up to seven days as history rather than a claim about now. One server error is enough to show. 4xx responses may be rejected inputs or application defects; the response code alone does not establish fault or an outage. One exception: when a teacher approves or rejects a hall-pass request, or a student cancels one, and the app can't find it at least three times in five minutes, making up more than 2% of hall-pass requests, Hall passes shows errors seen and the summary at the top flags it. That's a sign of a possible problem, not an outage.

We flag HTTP 5xx above 2%, HTTP 404 above 5%, hall-pass requests not found (at least three, above 2%), and p95 above 1,500 ms. p80 and p95 are the response times that 80% and 95% of requests came in under. Application requests include our own health checks.

The 30-day error tracker counts application responses in separate five-minute windows, so each observed request is counted once. Missing or stale monitoring leaves a gap. Successfully observed empty windows count toward coverage. Dates use UTC, including today; the latest unfinished window is excluded. Last-recorded times identify a window, not an individual request. Older reliability rollups cannot supply error totals.
