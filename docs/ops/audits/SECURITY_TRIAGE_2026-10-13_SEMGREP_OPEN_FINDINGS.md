### 2.2 Reachable production code that needs investigation

These are not Semgrep dispositions (the triggering findings are classified on their own rule in §3). They are owner decisions the triage surfaced.

1. **`resolve_issue` writes Store entitlement events from a Support route** (`app/routes/admin.py:10678-10812`, under `@requires_feat_context("FEAT-SUP-001")`; surfaced by finding 1014378791, rule `batch-import`). When a ticket is resolved with `reverse_transaction`, the route calls the Ledger's `reverse_transaction(...)` and Store's `lock_and_resolve_purchase_eligibility(...)`, then itself appends `EntitlementEvent(event_type='REVOKED', ...)` rows with `db.session.add` in the route body. `app/feats/transaction_void_feat.py` writes the same events on the ordinary reversal path. `INV-ARC-006` §VII: "`DOM` must own explicit mutation commands, and `FEAT` must never mutate state outside those commands"; `INV-ARC-000` §XI requires enforcing "no cross-domain mutation". `FEAT-SUP-001` has no entitlement or reversal clause. **Question:** should issue-driven reversal call the Store-owned revocation command instead of re-implementing it? Impact today: none observed (eligibility is checked; the event shape matches), but two copies of a revocation write can diverge.
2. **Grafana proxy route accepts POST/PUT/DELETE** (`app/routes/system_admin.py:874-878`, `grafana_proxy`, behind `@system_admin_required`; the `route-*` header findings at line 1061). **Investigated 2026-10-13 (read-only, owner-approved): unreachable in production.** Live nginx (`/etc/nginx/sites-enabled/classroom`, read with `nginx -T`) matches `infra/grafana-auth/nginx-grafana.conf`: `location = /sysadmin/grafana` returns its own `302` to `/sysadmin/grafana/`, and `location /sysadmin/grafana/` runs `auth_request` against Flask's `/sysadmin/grafana/auth-check`, then proxies straight to Grafana on `127.0.0.1:3000`. No request under either path reaches `grafana_proxy`, and the application journal, retained since 2026-10-07, records **0** requests to that endpoint. The CSRF-on-proxied-writes question therefore does not arise in production. **Proposed (not applied):** remove `grafana_proxy` as obsolete executable code, keeping `grafana_auth_check`, after confirming no test or document depends on it. Related: the live `grafana_ws_map.conf` forwards the client's own `Upgrade` header whenever no `Sec-WebSocket-Key` is present, so the `possible-nginx-h2c-smuggling` hardening item (§2.3) applies to production as well; it is behind the sysadmin `auth_request`.
3. **Repository and environment settings (not Semgrep findings; verified read-only via the GitHub API):**
   - The `production` environment's only protection is a branch policy (`main`). **No required reviewers**, so one dispatch deploys. `SOP-DEP-002` speaks of "environment approval".
   - The `github-pages` environment still allows `CTH_v2.0`, `github-pages` and `github_pages` besides `main`. None exist; anyone with write access who created one could publish the public docs site from an unreviewed branch.
   - Whether the repository's `sha_pinning_required` Actions setting exists or is on: **unverified** (the API did not return the field).

### 2.4 False positives and historical code

**A. Migrations.** All 102 Semgrep findings under migrations/ were traced individually at origin/main 0f704e660; every one is false_positive (SOP-SEC-002 §V.2 'false positive / mitigated, documented'). No finding splices table row data or any external input into SQL: interpolated tokens are module constants or literal call arguments, literal fragment choices, or (624c6b7223df lines 143/150 only) trigger names read from pg_trigger, which only a DDL-privileged role can write; the few DB-derived values (first_admin_id, feature_name, hall-pass payloads) are bind parameters. Live migrations run only via `flask db upgrade` from release-v2.yml (workflow_dispatch, production environment, 40-hex SHA) and pull_request CI against ephemeral DBs (no pull_request_target); app/ never imports or runs them. 36 findings are in migrations/archive/v1_196_migrations/, which Alembic never loads (dead code). SOP-DB-001 §V Rule 3 (and §V.B's ban on 'tidy, modernize, or re-lint') forbids editing merged migrations, so recommended action is documentation in a dated docs/ops/audits/ triage record plus out-of-file suppression: a .semgrepignore for migrations/archive/ and per-alert Semgrep triage for migrations/versions/ (never a path-wide exclusion of migrations/versions/ and never inline nosemgrep).

**B. Application code.** All 50 findings under app/ were traced at origin/main 0f704e660 (scan lines match HEAD; four main_line values are text-match artifacts: 1016492864, 1014378965, 1014378978 and the seven grafana route-* items). Dispositions: 44 false_positive, 6 hardening_opportunity, 0 confirmed_violation, 0 needs_investigation. The four critical generic-sql-flask hits are SQLAlchemy Core/ORM constructs with bound parameters and server-derived, class_id-scoped inputs. The open-redirects send to fixed url_for endpoints or pass is_safe_url/safe_redirect_target. The Markup sinks are escape()/bleach outputs already covered by the unsafe_jinja_filter_markup guard. The urllib/HTTPS calls go to fixed hosts. The security-header findings are covered by the app-wide set_security_headers hook, except X-Permitted-Cross-Domain-Policies, which nothing sets. Hardening items: that header (one line, closes three findings), a NaN pass-through on the client-asserted account-deletion hold gate, exception text in an audit-failure log line, and Host-derived _external URLs with no TRUSTED_HOSTS. Side observation outside the SAST rule: admin.resolve_issue writes Store-owned REVOKED entitlement events inline in the route (admin.py:10796), and this deserves an INV-ARC-006 review.

**C. Templates and static assets.** 62 findings in templates/ and static/ at 0f704e660; no confirmed violations. All 31 django-no-csrf-token hits are false positives: Flask-WTF CSRFProtect is global with no exemptions and every flagged POST form already carries a csrf_token()/form.csrf_token/hidden_tag() token. Of 28 missing-integrity hits, 11 Turnstile loaders are FP (SRI infeasible; CSP pins origin) and 17 are hardening: the 8 EasyMDE tags are the most material because the jsDelivr URL is unpinned (floating latest, so SRI cannot be added), then 4 passwordless.dev SDK tags on login/passkey pages, then 5 pinned assets (font-awesome@4.7.0 CSS x3, zxcvbn@4.4.2, chart.js@4.4.0). No normative INV/DOM/SPEC document requires SRI, and CSP allows 'unsafe-inline'/'unsafe-eval', so CSP does not compensate for a tampered CDN script. The three interpolation/format-string hits interpolate only server constants or numbers and are FP.

**D. CI, ops and tooling.** 56 findings triaged at origin/main 0f704e660: 45 hardening_opportunity, 11 false_positive, 0 confirmed_violation, 0 needs_investigation. The 39 mutable-tag findings (38 on main; 1016273266 exists only on Dependabot PR #1565) are all GitHub-owned actions left unpinned after #1546 pinned the third-party ones; the highest-weight are in release-v2.yml, the deploy-status deploy job and github-pages, which run under environments restricted to main but with no required reviewers. No workflow uses pull_request_target; both shell-injection findings interpolate github.base_ref in read-only pull_request jobs that already execute PR code, so they are false positives (optional env-var fix). The backup SQL was already fixed with sql.Identifier, the scripts are operator-only or parse-only, and the .claude hit is a documented counter-example. Hardening proposals: SHA pins plus the repo setting sha_pinning_required (currently false), Dependabot cooldown, a non-root USER for the Cloud Run status image, a websocket-only Upgrade map for the Grafana nginx block, and quoting or removing the v1 reset utilities.

Key traced facts the false-positive calls rest on (re-verified by the reviewer, §4):

- SQL: every `text()`/f-string in `migrations/` interpolates module constants, literal arguments, or (in `624c6b7223df`:143,150) a double-quoted trigger name from `pg_trigger`; runtime values are bound parameters. 36 findings are in `migrations/archive/v1_196_migrations/`, which Alembic never loads (no `script_location`/`version_locations` override; Flask-Migrate loads `migrations/versions/` only).
- The four `critical` `generic-sql-flask` findings are SQLAlchemy Core/ORM statements with bound parameters: `sa.update(...).where(...).values(...)` (`teacher_recovery_feat.py:259`), `insert(...).values(...).returning(...)` (`admin_identity_service.py:62`), ORM `.filter(...)` expressions scoped by `class_id` (`ledger_balance_query_service.py:124,132`).
- CSRF: one app-wide `CSRFProtect` (`app/extensions.py:24`, `app/__init__.py:353`), no `csrf.exempt` in `app/`; all 31 `django-no-csrf-token` forms carry `csrf_token()`, `form.csrf_token` or `form.hidden_tag()` (a Django-only rule).
- Redirects: four go to fixed `url_for` endpoints; the one `redirect(next)` (`student.py:3090`) is guarded by `is_safe_url`.
- CI shell interpolation: no workflow uses `pull_request_target`; the two `run-shell-injection` sites interpolate `github.base_ref` in plain `pull_request` jobs with read-only tokens.
