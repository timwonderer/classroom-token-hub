## Deviations from SOP-DEP-001

**1. §IX.1–3 (fresh database) not performed — deliberate.**
§IX is written for a first deployment and directs the operator to create one
empty database. This is a redeploy that continues the same §XI campaign, and a
fresh database would destroy its state: two classes, a 30-seat roster, the rent
cycle, the ledger history, and the attendance rows that evidence the
daily-limit verification recorded earlier today. The database was preserved and
the migration applied to it. That is also the more realistic exercise — every
future production deploy applies migrations to populated data, which §IX.1 never
tests. Data confirmed intact afterwards: 2 classes, 62 seats, 4 attendance
sessions, 7 ledger transactions, 1 bill cycle.

**2. §VII.1 (maintenance/holding mode) not used — operator direction.**
Maintenance mode was enabled at the start of this deploy and confirmed working
(`/` returned 503 with the Scheduled Maintenance page, `/health` stayed 200),
then reverted at the operator's instruction: the application is gated by
Cloudflare Access, which is the access control they intend to use for future
maintenance windows as well. §VII.1 should be amended to reflect that;
`SOP-DEP-001` §XVII governs amendments. Recorded here rather than amended
unilaterally.

**3. §VII.2 `git status --porcelain` not empty.**
It reports `?? venv.old/`, an untracked leftover from a prior virtual-environment
rebuild. No tracked file differs from the tag, so the deployed tree matches the
release. Not removed: deleting host files outside the scope of this deploy is
not something this procedure authorizes.

**§XVI is not met by this deployment and is not claimed.** Its completion
condition requires the SHA to run from a *fresh* database; deviation 1 is
incompatible with that by design. §XVI attaches to the campaign, which remains
open pending the §XI items listed below.
